# Архитектура C# Distributed Git Storage

**Русский** | [English](architecture.en.md)

## Компоненты

- **Web Control Plane** хранит placement, предоставляет REST API и публичный Git URL `/{name}.git`.
- **PostgreSQL** хранит кластеры и узлы, placement, текущее поколение, состояние реплик и очередь репликации.
- **Storage Node** хранит bare-репозитории и предоставляет внутренние management и Git Smart HTTP endpoints.
- **System Git** выполняет операции с object database, refs и packfiles.

## Создание

Control Plane выбирает из PostgreSQL активный кластер с наименьшим количеством репозиториев, выбирает его primary методом round-robin, создаёт одинаковый bare-репозиторий на всех активных узлах этого кластера и затем сохраняет placement с `StorageClusterId`. При ошибке БД выполняется компенсирующее удаление. Добавленная в БД активная нода подхватывается reconciliation и получает копии существующих репозиториев своего кластера.

## Чтение

Для `clone`, `fetch` и `pull` Control Plane выбирает только реплику со статусом `Healthy`, поколение которой совпадает с текущим поколением репозитория. Сначала проверяется primary, затем остальные актуальные копии. Если такой копии нет, возвращается `503`; устаревший репозиторий клиенту не выдаётся.

## Запись и репликация

Перед `git push` Control Plane берёт PostgreSQL advisory lock для конкретного репозитория. Это не позволяет двум экземплярам приложения одновременно менять его refs. После блокировки повторно читается placement и выбирается доступная актуальная реплика.

До изменения Git создаётся новое поколение и копии помечаются ожидающими синхронизации. Успешный `git receive-pack` выполняется на выбранной ноде, после чего её refs fingerprint фиксируется как актуальный, а для остальных нод в той же БД сохраняются задания репликации. Затем Control Plane синхронно реплицирует и проверяет копии до достижения `WriteQuorum` (по умолчанию 2). Только после этого клиент получает успешный результат push.

Фоновый worker забирает задания с lease и выполняет на целевой ноде:

```text
git fetch --prune --force <source-node> +refs/*:refs/*
```

Затем worker сравнивает fingerprint источника и результата. Совпавшая копия получает `Healthy` и актуальное поколение. При ошибке задание остаётся в очереди с exponential backoff, а реплика помечается `Lagging` или `Unavailable`. Reconciliation восстанавливает пропущенные задания после перезапуска. Если исходная нода исчезла, worker может взять другую актуальную healthy-копию.

## Гарантии MVP

- конкурентные записи одного репозитория сериализуются PostgreSQL advisory lock;
- подтверждённый push имеет не меньше `WriteQuorum` актуальных физических копий;
- устаревшие копии исключены из чтения и не могут незаметно стать primary;
- очередь переживает перезапуск, имеет lease, retry и reconciliation;
- при обрыве HTTP-запроса процесс Git завершается вместе с дочерними процессами до освобождения ресурсов запроса;
- C# не реализует внутренний Git object/pack format, а использует установленный Git.

Репликация до quorum синхронная, а оставшихся копий — асинхронная. Если quorum не достигнут за `WriteQuorumTimeoutSeconds`, клиент получает protocol-level ошибку Git с ID репозитория, поколением и числом актуальных копий. При этом основная нода уже могла принять refs, поэтому результат считается неопределённым до проверки или безопасного повторного push; постоянная очередь продолжает синхронизацию.
